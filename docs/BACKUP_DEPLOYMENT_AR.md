# النسخ الاحتياطي اليومي لـ SWS — دليل إعداد خارجي

قاعدة البيانات والملفات الحساسة لا يجب نسخها باستخدام مفتاح سري داخل تطبيق Flutter. شغّل النسخ الاحتياطي من جهاز إدارة موثوق أو خادم خاص، مع تشفير القرص وحماية مجلد النسخ.

## المطلوب

- PostgreSQL client tools (`pg_dump` و`psql`) متوافقة مع إصدار Supabase.
- اتصال قاعدة البيانات من `Project Settings → Database` (متغير `SWS_DB_URL`).
- المفتاح السري `service_role` كمتغير بيئة على الجهاز الموثوق فقط (`SWS_SERVICE_ROLE_KEY`) لتنزيل ملفات Storage.
- مساحة نسخ احتياطية منفصلة ومحمية. لا ترفع النسخ إلى مجلد عام أو Git.

## نسخة قاعدة البيانات

يمكن استخدام `pg_dump` لتصدير مخطط `public` وبيانات التطبيق:

```powershell
$stamp = Get-Date -Format 'yyyyMMdd_HHmmss'
New-Item -ItemType Directory -Force -Path '.\backups' | Out-Null
pg_dump "$env:SWS_DB_URL" --schema=public --no-owner --no-privileges --format=custom --file ".\backups\sws_public_$stamp.dump"
```

احتفظ أيضًا بنسخة من ملفات SQL الخاصة بالمشروع. تذكّر أن تصدير `public` وحده لا ينسخ مستخدمي Supabase Auth أو إعدادات المشروع؛ وثّق بريد حساب الإدارة وإعدادات المشروع بشكل آمن، ولا تحفظ كلمة المرور داخل النسخة.

## نسخة ملفات Storage

أنشئ مهمة موثوقة تستخدم Supabase Storage API بمفتاح `service_role` محفوظ كمتغير بيئة لتنزيل كل الملفات من bucket `sws-private-documents` إلى مجلد مؤمّن. لا تضع المفتاح في ملف PowerShell محفوظ أو داخل المشروع. اختبر أن كل `storage_path` الموجود في `public.traveler_documents` له ملف مطابق في النسخة.

## الجدولة والاختبار

1. أنشئ مهمة Windows Task Scheduler يومية لتشغيل أوامر النسخ بعد ساعات العمل.
2. احتفظ بنسخ متعددة وفق سياسة الشركة (مثل 30 نسخة يومية) واحذف النسخ القديمة فقط حسب سياسة معتمدة.
3. سجّل نجاح/فشل كل تشغيل، وأرسل تنبيهًا عند الفشل.
4. دوريًا، استعد قاعدة البيانات والملفات في مشروع Supabase منفصل، وتأكد من سلامة ملفات المسافرين والحركات المالية وروابط المستندات.

**تنبيه:** إعداد Supabase نفسه لا يُفعّل مهمة نسخ مستقلة تلقائيًا من هذا التطبيق. يجب إعداد المهمة خارج Flutter والتحقق من نجاحها قبل إدخال بيانات إنتاجية.
